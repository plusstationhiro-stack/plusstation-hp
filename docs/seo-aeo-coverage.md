## 7要素 × サイト全体の置き場

### 1. 構造化データ（Schema）

| どこ | 何を出すか |
|------|------------|
| 全ページ共通 | `Organization`（NAPと一致） |
| トップ | `WebSite` |
| `/app` | `SoftwareApplication` + `FAQPage` |
| `/team` | `Service` + `FAQPage` |
| `/news` 各記事 | `NewsArticle` または `Article` |
| `/company` | `Organization` 詳細＋任意で `Person`（代表） |
| 下層 | `BreadcrumbList` |

→ 「ページを増やすたびに Schema 種別が決まる」IAになっている。

### 2. 専門性の明示（資格・経歴）

| どこ | 内容 |
|------|------|
| `/team` | 専門性セクション（資格・顔は**テキストでも**書く。画像だけ禁止） |
| `/app` | コンテンツ監修がある場合のみ、根拠付きで短く |
| `/company` | 代表・会社としての信頼 |
| 禁止 | 根拠なき「医師監修」「国内No.1」 |

→ 現状 **正式な資格文字列はオーナー確認待ち**（設計枠だけ確保）。

### 3. 実績の量と質

| どこ | 内容 |
|------|------|
| トップ | NEWS枠（最新1件の要約） |
| `/news` | 一覧（量を増やせる受け皿） |
| `/news/cheval-...` 等 | 個別記事（質＝固有名・何をしたか） |
| `/team` | 実績への内部リンク |

→ 旧HPの「NEWSを1ブロック置いて終わり」から、**記事URLが増える構造**に変更。

### 4. サイテーション（外部言及）

サイト側でできること:
- 引用しやすい固定URL（`/news/...`）
- NAPの表記ゆれをなくす（外部が社名を書くときの正を示す）
- 導入先への「公式サイトからリンクしてください」依頼文（運用）

ジェッツ等は発表後に記事追加 → 相手サイト・SNSからの言及を取りに行く、という順序。

### 5. 一貫したブランド情報（NAP）

正（全ページフッター＋会社＋特商法＋Schemaで同一）:

- 株式会社 Plus Station  
- 〒130-0013 東京都墨田区錦糸2-9-3-502  
- 090-6288-4171  
- plusstation.hiro@gmail.com

→ 旧Studioで弱かった「会社情報の一貫性」を、**フッター必須＋company＋tokusho**で担保する設計。

### 6. H1・title・キーワードの整合

| ページ | 役割（検索意図） | title/H1の型 |
|--------|------------------|--------------|
| `/` | ブランド・会社 | 会社＋二本柱の意味 |
| `/app` | 個人アプリ検討 | 自主トレ・体調・動画・記録 |
| `/team` | チーム導入検討 | チーム・コンディション・自主トレ支援 |
| `/company` | NAP・会社 | 会社概要 |
| `/news` | 実績・お知らせ | 導入実績・パートナーシップ |
| 法的 | コンプライアンス | 規約名そのまま |

ルール: **1ページ1主キーワード**。感情コピーはサブ。H1を画像の文字だけにしない（HTML本文に出す）。

### 7. ページ内の専門性スコア（E-E-A-T）

| 要素 | サイト全体での出し方 |
|------|----------------------|
| Experience | `/news` の実名実績、現場の運用（未入力・席モデル等） |
| Expertise | 資格・経歴テキスト、分析は「目安」（医療でない注記） |
| Authoritativeness | 実績記事の蓄積、被リンク、発表後の強チーム表記 |
| Trust | NAP、法的3点、RLS説明、誇大禁止リスト、個人/チーム混同しない |

## ニュースを「HPから更新しやすくする」設計

要件として明示されたので、実装方針を先に固定する。

### 推奨（静的サイトのまま更新しやすく）

```
content/news/
  2025-xx-cheval.md   ← 記事を足すだけ
  ...
```

- ビルド時に一覧生成、または小さな `news.json` を手編集
- トップのNEWS枠は「最新1件を自動表示」
- 各記事に Schema `Article`、固有の title/H1/description

### 将来（もっと楽にする）

- headless CMS（例: microCMS）や Notion → 静的生成  
- 今はコード量を抑えるなら **Markdown / JSON 追加方式**で十分

### 公開ルール（運用）

| 状態 | サイト |
|------|--------|
| CHEVAL | 掲載可（表記ゆれ統一） |
| 千葉ジェッツ等 | 契約・発表OKになるまで **記事ごと作らない** |
| 下書き | `draft: true` でビルド除外 |

→ 「ニュース枠はあるが更新しづらいStudio」から、「記事を足すとトップにも載る」構造へ。

## まだ「設計枠だけで中身待ち」のもの

1. キーワードの最終語（Search Console後に微調整）  
2. 資格・経歴の正式文言  
3. 価格抑制をHPに書くか（営業のみか）  
4. ニュース更新方式の最終選択（MD vs JSON vs CMS）  
5. ジェッツ等の公開タイミング

## 一言

これらは「トップにキーワードを詰め込む」のではなく、**ページ役割を分けたうえで、Schema・NAP・実績URL・専門性テキスト・title/H1ルールを全ページ共通の型にした**、という意味でサイト全体に織り込んでいる。  
ニュースは、そのうち **実績・サイテーションの増設口**として、更新しやすい `/news` 構造を前提にしている。
